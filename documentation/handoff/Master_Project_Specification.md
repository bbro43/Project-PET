# Reconstructed master specification
## Confirmed user scope
Build a standalone mobile Mega Man Battle Network simulator faithful to the GBA Battle Network 4–6 games, not a generic grid fighter. Use all six versions as reference: BN4 Red Sun/Blue Moon, BN5 Team ProtoMan/Team Colonel, BN6 Cybeast Gregar/Cybeast Falzar. Preserve version-specific differences and original visual/audio/combat behavior. Every Navi should be selectable as a player and CPU, with original techniques, movement, timing, and attack patterns. Menu shows selected Navi. Include transformations and version-specific mechanics. Include selectable virus battles, endless survival waves, Navi-versus-Navi NetBattle, BattleChip system and folder editor, and private online battles between mobile devices for parent and child.

Navi Customizer is a core feature for every Navi: HP, charge shot, Air Shoes, Undershirt and other BN4–6 programs; reproduce original grid, program shapes, placement rules, bugs and per-Navi saved configurations. Preserve original behavior rather than substituting arbitrary buffs.

Mobile app installed from GitHub Pages; updates should arrive through the existing installation. Increment app version on every release and asset pack number when assets change. Keep project on existing main branch deployment; eventual private repository. Verify private hosting compatibility before changing visibility. User questioned the name Signal Yard: it is a prototype label, not the intended final identity.

## Implementation guidance (proposed, not recovered verbatim)
- Build an asset registry with stable IDs, source game/region/ROM hash, offset, palette, frame bounds, anchor, sequence timing, flags, provenance and confidence. Retain original bytes separately; deduplicate by hash without losing references. Extract sprites, portraits, effects, panels, UI, chips, viruses, transformations, music and sound effects where authorized. Do not invent labels or claim unverified animation mappings.
- Implement a deterministic fixed-tick simulation separated from rendering, input, AI and networking. Validate 6x3 panel ownership, movement, terrain, hitboxes, damage, invulnerability, charge, attack startup/recovery, chip selection and custom gauge against game-specific evidence. Define version rules explicitly rather than blending incompatible mechanics silently.
- Model player and CPU moves using shared attack definitions with distinct input/AI dispatch. CPU patterns should be verified against original encounters, including variants and phases. Use a complete roster coverage matrix; distinguish extracted, identified, animated, playable, CPU-verified and tested.
- Build folder editing, chip codes and legality, chip selection and execution, saved profiles, customization and transformations with version-aware rules. Validate each against source games.
- Provide touch controls, readable HUD, responsive pixel-art rendering, offline solo play and persistence. Keep existing install identity and relative paths stable. Use private room codes and an authenticated or otherwise secured multiplayer transport; GitHub Pages alone is static and cannot host an authoritative multiplayer server. Test synchronization, reconnects, latency and disconnects on two phones.
- Maintain tests, asset manifests, release notes, audit logs and checkpoint ZIPs. Do not declare complete until coverage and acceptance tests demonstrate the intended behavior.
